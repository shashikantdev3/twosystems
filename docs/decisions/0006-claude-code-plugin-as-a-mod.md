# 0006: The Claude Code plugin is a mod, with one event file per session

**Status:** Accepted, 19 October 2026

## Context

Claude Code runs *mods* (since 2.1.287; this plugin needs 2.1.303, the version it is built and tested with): plugins whose JavaScript or TypeScript hooks run inside Claude Code itself, in the terminal, the Desktop app's Code tab and the VS Code extension. A mod sees every prompt, tool call, model request (with its exact token counts) and turn; it can draw a band above the prompt with buttons (terminal and Desktop only; a pane is drawn on every surface); it can answer a tool call's permission check with "ask", which goes to the permission mode's decider: Claude Code's dialog in the default, accept-edits and plan modes, but a classifier, a denial or nothing in the others. Where an organization manages Claude Code, the classic hook events and `session.compact` do not reach a plugin a person installed. It cannot use Node: its file system, network, clock and environment come from Claude Code's `$` interface, and `claude plugin validate` lists every one of those calls before a user installs it. A mod cannot append to a file; it can only read and write whole files.

The `twosystems hook` command (decision 0005) already works with Claude Code's settings hooks, but it needs Node and npm, a hand-edited `settings.json`, and a transcript file to read usage from, and it cannot draw anything.

## Decision

- The Claude Code plugin is a mod in `packages/claude-code`, installed from this repository's marketplace file (`.claude-plugin/marketplace.json`, marketplace `twosystems`).
- It runs the same decision code as the hook command. The part of the core that needs no Node (signals, redaction, state, questions, engines, the pipeline, receipt maths, record builders, messages) is reachable from `packages/core/src/portable.ts`; a test fails if anything there imports a Node module or uses a Node-only global. `scripts/sync-shared.mjs` copies those files into `packages/claude-code/hooks/core/`, and CI fails if the copy is stale. Engines take Claude Code's fetch, and the pipeline takes Claude Code's clock for its timeout.
- Stuck check: a `tool.check` hook runs the rule signals on every call and the decision model at most once every five calls per loop, only on evidence since the last check. It answers "ask" only when the permission mode Claude Code last reported for that loop (from the classic `UserPromptSubmit`, `PostToolUse` and `PermissionRequest` events) shows a dialog; with no mode reported it stays silent rather than guess. The decision record waits for the classic `PermissionRequest` event, which says the dialog appeared: the plugin hooks it, lets the hooks beneath answer first, and counts the dialog as shown only when none of them answered, for the pending question with the same tool and the same input (the event carries no call id). The tool call's outcome then records whether the user let it run (`keep_going`) or not (`stop`). An ask that never reached a dialog is recorded as `not_shown`, with no user action. A live terminal session on 2.1.303 confirmed this path: a mod's ask raised the dialog, `PermissionRequest` reached the plugin with the same input as `tool.check`, and Yes and No gave the outcomes the plugin reads. In auto mode the same ask went to the classifier, with no dialog and no `PermissionRequest`, as expected.
- Fresh-start check: a band above the prompt with Clear, Compact and Keep going (a pane on surfaces without the band, such as VS Code), raised after a turn when the conversation has grown large, and after an idle spell longer than the prompt cache lifetime. A prompt typed at the terminal that looks like a different task in a large conversation is held (dropped and kept in the band) until the user chooses Clear then send, Compact then send, Send as is, or Edit; it is sent with `asUser`, so Claude reads it as the user's own words. Prompts with `@` mentions or images are never held, because a re-sent prompt would not expand them. A held prompt is not dropped: a typed `/clear`, `/compact` or other prompt, a `/resume`, a failed action or a closed pane puts it back in the prompt box, after anything typed there since; when the box cannot take it (a dialog holds the keys), it keeps waiting, whole, in the band, marked as already answered so a later press is not counted twice. Prompts sent from the Desktop app or VS Code arrive as the SDK host's and are never held, but they take a suggestion down like a typed one. The band is claimed and taken with a versioned write, so two checks or two presses never overwrite or repeat each other. A `/clear` or `/compact` the user types within 15 minutes of a suggestion counts as taking it; automatic compaction does not.
- Records: exact usage for every main-loop request (from `turn.step`), the usage of every compaction's own request (recorded as cost, with no context size), every decision and every user choice. Because a mod cannot append, each session writes its own files, `~/.twosystems/events.d/claude-code-<session>[-<part>].jsonl`, each part under 256 KB and rewritten whole through one queue, so parallel hooks never lose a line and a write cut short by a crash costs little. The home folder is the one Node's `os.homedir()` gives, so the `twosystems` command reads the same folder: USERPROFILE on Windows, HOME elsewhere. A mod cannot ask which system it runs on, so USERPROFILE counts only when it is a Windows path and HOME is unset, a Windows path or a Git Bash drive path; WSL can forward USERPROFILE to Linux. The event log is now `events.jsonl` plus every `.jsonl` file in `events.d/`; `twosystems receipt` and `doctor` read both, and an event that appears twice is counted once.
- Checks run only when a surface is attached (terminal, Desktop, VS Code, phone). In `claude -p` and the Agent SDK, where an "ask" would block or fail automation, the plugin only records usage.
- A suggestion chosen to be shown whose moment passed before it could appear (a turn started during the model call, another suggestion held the band, no surface could draw it, a pane was not placed, no dialog appeared) is recorded with reason `not_shown`. The receipt does not count it as seen, but keeps it in the comparison as the coin flip assigned it: the held-out group cannot be screened the same way, so dropping moments from one side would bias the verified saving. Missed moments dilute the measured effect toward zero; they do not tilt the comparison.
- Until calibration (Sprint 3) the plugin's false-alarm level is a plain shift of the built-in thresholds, labelled as such; the lock hash changes with it, so receipts keep the settings apart.

## Consequences

- One install line, no Node, and receipts from exact token counts, so Claude Code receipts can be verified.
- The plugin and the hook command must not both run in one session, or the user may be asked twice. The plugin warns when it finds `twosystems hook` in the settings.
- The mods API is new and may change between Claude Code releases. CI pins the Claude Code version the plugin is validated and tested with, and moves it on purpose.
- The plugin keeps recent observations in memory, not on disk, so a reload of the plugin (for example after a `/config` change) or a restart of Claude Code starts them afresh; only the event records persist. A stuck question still open at a reload, or when the process is killed, is not recorded. Held-out decisions are written at once, so this rare loss falls on the shown side only; Sprint 5 closes it.
- The Python package reads one file at a time for now; reading `events.d/` comes with the calibration commands in Sprint 3.
- The receipt line appears only under the next answer after twosystems did something, rather than under every answer as first planned, to keep the transcript quiet.
- Where an organization manages Claude Code, the stuck check is silent, and a typed `/compact` or an automatic compaction is neither counted as taking a suggestion nor recorded as cost (only the band's own Compact records its cost), because the events that carry the permission mode and compaction do not reach a user-installed plugin there.
