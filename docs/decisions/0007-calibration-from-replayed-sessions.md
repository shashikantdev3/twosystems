# 0007: Calibration from replayed sessions, split between the core and the Python package

**Status:** Accepted, 19 October 2026

## Context

The thresholds that turn a decision model's probability into "act", "unsure" or "silent" are cautious guesses until they are fitted on labelled moments (decision 0003, roadmap Sprint 3). Fitting needs, for each moment, the probability the live check would have got and a person's label. The probability depends on the exact redacted summary the live check sends, which the TypeScript core builds; Claude Code keeps every session as a JSON Lines transcript under `~/.claude/projects/`. The Python package is the calibration kit (decision 0001), and should not rebuild the summary itself: a second implementation would drift, and a threshold fitted on a different summary does not transfer.

## Decision

- **Moments come from the core, at the plugin's check points.** `twosystems moments` (npm) reads saved Claude Code sessions line by line and replays each one the way the Claude Code plugin watches a live session, with the same rules: a stuck check before a tool call, at most once every five calls, on the evidence since the last check (trigger `tool`); a fresh-start check when a turn ends (`turn`), asked again only once the conversation has grown by half and started over after a compaction; one when the session sat idle past the prompt cache lifetime and half a minute (`idle`); and one when a typed prompt without an @ mention or pasted image looks like a new task in a conversation of 20,000 tokens or more, the moment the plugin holds it (`prompt`). A turn ends at the agent's last output, before whatever comes next (a prompt, a command, a notification, or a compaction between turns, which the plugin sees only after the prompt that caused it); the idle check runs at that point in time whatever comes next. Stuck moments are skipped in a permission mode where Claude Code shows no dialog, as the plugin does, when the transcript records the mode. The context window is the one the session ran with as far as the transcript shows it (1M tokens when a request was larger than 200,000, else 200,000; `--window` overrides it). Wherever a rule signal fires, it keeps a *moment*: the redacted summary the decision model would have read, its hash, the signals, the question's hash and labels, and a few redacted lines of what happened next, for the person labelling. The replay cannot know which suggestions a live session would have shown, so it keeps every moment the rules reach. Subagent loops are left out for now.
- **A moment's id survives a new export.** It is a hash of the decision, trigger, session and time. Exporting again keeps the label and replaces the summary and "what happened next"; scores stay only while the question and the summary are the same. Copies of a moment that Claude Code made by forking or resuming a session are dropped unless labelled, and the fit counts labelled copies once.
- **Scores come from the core too.** Every moment gets a free score from the rules engine. With `--score` (or `--rescore` for a drift check) the configured decision model is asked the exact question the live check asks, with the same summary.
- **One file between the two halves.** `~/.twosystems/moments.jsonl`, one moment per line, described by `schemas/moment.schema.json` and validated by both languages with the same rules and messages as the other shared files. It holds redacted session text, so it stays on the machine like the session transcripts it comes from, readable by its owner only. A file with a line that does not validate, or with an id used twice, is never overwritten, so labels are never lost to a bad line. Both languages write it under the same lock file and merge onto what is on disk, so labelling while `twosystems moments` runs loses nothing; a score that could not be stored is dropped, never the moment.
- **Labelling, fitting, checking and reporting are Python.** `twosystems-calibrate label` asks one key per moment, taking one moment from each session in turn in a fixed shuffled order, and saves every answer; the model's answer is hidden unless `--show-model` is given, so it cannot sway the person by default. `fit` gives each decision one act threshold, shared by the labels that lead to a suggestion, chosen by fixed-sequence testing (Learn then Test): thresholds are tried from 1.00 down in steps of 0.01, each accepted only while the one-sided Clopper-Pearson upper bound on its false-alarm rate (acting when the label was something else) stays at or below the target (default 5% at 95% confidence), and the descent stops at the first failure. Testing in a fixed order and stopping at the first failure is what keeps the confidence honest over many thresholds; thresholds that act too rarely for the bound ever to pass are skipped first, which depends on the scores alone. Of the accepted thresholds, the fit keeps the one that acts on the most fitting moments and, among those acting on the same moments, the highest. The fit uses the answers of one model version, the newest; moments scored only by an older one are left out until rescored, because a lock fitted on two models' answers fits neither. The unsure threshold is the lowest at which moments shown as unsure get the label right at least half the time. A fixed share of sessions (default a quarter, chosen by a hash of the session id) is kept out of fitting and used to test the thresholds; the test gives a verdict only when it has enough acts to. Same input, same output: there is no randomness, and the lock's date is the newest label's. `check` fails on a reworded question, a new model version, drift between each moment's last two scorings, or false alarms above the target with the newest answers. `report` writes one self-contained HTML page.
- **Probabilities are used as the engine gives them** (`calibration: none`). For a threshold rule, any calibration map that keeps the order of probabilities only moves the thresholds, so it adds nothing here.
- **A fitted lock reaches every adapter, and only where it applies.** The hook command already reads `decisions.lock` with the full schema validator. The plugin now reads `~/.twosystems/decisions.lock` once per load with a light structural check (it cannot run the schema validator) and uses it in place of the built-in thresholds; the false-alarm level setting then no longer applies, and `/twosystems` says per decision whether the lock applies. An entry is used only for the engine and question it was fitted for, and only while the model reports the version it was fitted on (when either side gives no version, the lock is trusted); otherwise the built-in thresholds apply and the decision is logged as a lock mismatch. A decision missing from the lock keeps the built-in thresholds without being flagged. Thresholds apply to the probabilities rounded to four places, as logged and as the fit saw them. The holdout share in the lock is a record of what was asked for; at run time the share still comes from the adapter's own setting.
- **The threshold rule is shared.** `schemas/examples/threshold-cases.json` holds the expected band for a set of probabilities and thresholds, and both languages run it, so the Python fit and the TypeScript runtime cannot disagree on what a threshold does.

## Consequences

- Labelling needs Node.js 22 (for `twosystems moments`) and Python 3.10 or newer on the machine that holds the sessions.
- The fit is only as good as the labels, and labels are one person's judgement with hindsight. Showing "what happened next" makes labels more accurate but is information the live check never has, so the fitted thresholds may be a little optimistic; the test sessions and `check` are there to catch that.
- The bound assumes the labelled moments are independent draws from the moments to come. Moments from one session are alike, so the confidence is a little optimistic; labelling one session at a time in turn spreads the labels, and the test sessions give a second look.
- With few labels the bound is strict: at a 5% target and no false alarms it takes at least 59 acts on the fitting part before any threshold qualifies. The fit says so instead of writing a weak lock.
- The replay is close to, but not exactly, the plugin: it does not know which suggestions a live session showed (a shown suggestion can make the plugin skip a later check), it infers the context window, it cannot tell a prompt typed in the terminal from one sent from the Desktop app or VS Code (only terminal prompts are held), and it finds no idle check after the last turn of a session. The question is the same at every trigger, so thresholds carry over; the label screen words the question for the trigger.
- Moments built for an older wording of a question, or whose summary comes out different, keep their labels on the next export and lose their old scores.
